# Krpc 与 gRPC 端到端 QPS 测试结果

测试日期：2026-07-24

## 1. 结论

本次测试在同一台虚拟机、同一个 loopback 网络环境下进行。每个正式样本均发起
1,000,000 次 RPC，逻辑并发均为 1000，业务函数不包含休眠或其他模拟业务耗时。

| 端到端调用链 | 三轮成功 QPS | 平均成功 QPS |
| --- | ---: | ---: |
| Krpc 线程客户端 -> Krpc Provider | 51,962.1 / 57,452.2 / 53,467.0 | **54,293.8** |
| Krpc 协程客户端 -> Krpc Provider | 58,847.2 / 50,399.3 / 60,611.2 | **56,619.2** |
| gRPC 同步客户端 -> gRPC 同步服务端 | 18,770.3 / 19,910.9 / 20,222.4 | **19,634.5** |
| gRPC 异步客户端 -> gRPC 异步服务端 | 38,261.7 / 44,177.3 / 47,526.7 | **43,321.9** |

按三轮算术平均值比较：

| 比较组 | 结果 |
| --- | --- |
| Krpc 协程版 vs Krpc 线程版 | 协程版高 **4.28%** |
| Krpc 同步线程版 vs gRPC 同步版 | Krpc 高 **176.52%**，即约为 gRPC 的 **2.77 倍** |
| Krpc 协程版 vs gRPC 异步版 | Krpc 高 **30.69%**，即约为 gRPC 的 **1.31 倍** |

这里测到的是当前实现、当前参数和当前机器上的完整框架吞吐量，不是一个可以脱离
测试条件泛化的“框架官方性能结论”。尤其不能据此直接宣称 Krpc 在所有负载下都比
gRPC 快 2.77 倍。

## 2. 测试口径

- 构建类型：Release。
- 网络：客户端和服务端位于同一台机器，通过 `127.0.0.1` 通信。
- 请求：`Login(name="zhangsan", pwd="123456")`。
- 响应：固定返回 `errcode=0`、空错误消息和 `success=true`。
- 业务耗时：无 `sleep`，不执行数据库、磁盘或第三方服务访问。
- 逻辑并发：1000。
- 每个线程或异步调用链的请求数：1000。
- 每轮总请求数：1,000,000。
- QPS 口径：`成功响应数 / 客户端 RPC 阶段墙钟时间`。
- 每组正式运行三轮，表格报告三轮原始值和算术平均值。

Krpc 协程客户端退出时，`IOManager` 还会等待约 5 秒完成调度器关闭。该时间发生在
全部 RPC 已完成之后，因此不把关闭等待计入 RPC QPS。协程客户端当前打印的
`rpc qps` 实际是“总请求数 / RPC 时间”；出现失败时，本文改用“成功数 / RPC 时间”
重新计算成功 QPS。

## 3. 四种端到端实现

### Krpc 线程版

- 服务端：项目现有 Krpc Provider，Muduo 网络层，400 个业务线程。
- 客户端：1000 个原生线程，每个线程顺序执行 1000 次同步 RPC。
- 连接：预热 1000 条 Krpc TCP 长连接，请求结束后归还连接池并复用。

### Krpc 协程版

- 服务端：与线程版使用同一个 Krpc Provider，400 个业务线程。
- 客户端：4 个 `IOManager` 工作线程调度 1000 个协程，每个协程顺序执行 1000 次 RPC。
- 连接：同样预热并复用 1000 条 Krpc TCP 长连接。

### gRPC 同步版

- 服务端：gRPC 1.51.1 同步 Service，4 个 CompletionQueue，每个 CQ 最少 4 个、最多
  100 个 poller，即最多约 400 个 poller。
- 客户端：1000 个原生线程，每个线程顺序执行 1000 次同步 unary RPC。
- 连接：所有 Stub 共享一个 gRPC Channel，由 gRPC 使用 HTTP/2 管理和多路复用。

### gRPC 异步版

- 服务端：gRPC `AsyncService`，4 个 CompletionQueue 消费线程，预挂 1000 个
  `Login` 请求对象。
- 客户端：4 个 CompletionQueue 消费线程驱动 1000 条异步调用链，每条调用链顺序
  执行 1000 次 unary RPC。
- 连接：使用一个共享 gRPC Channel 和 HTTP/2 多路复用。

同步组比较的是完整的“同步客户端 + 同步服务端”，异步组比较的是完整的“协程/异步
客户端 + 对应服务端”。没有让 gRPC 客户端调用 Krpc Provider，也没有只替换客户端。

## 6. Krpc 线程版失败样本说明

固定三轮正式样本中的前两轮均为 1,000,000 次成功；第三轮成功 999,889 次、失败
111 次，表中使用的是该轮的成功 QPS 53,467.0。失败原因全部为：

```text
Borrow connection from pool failed!
```

为确认这不是输出误读，随后额外复测一轮，得到成功 QPS 54,154.2，成功 997,001 次、
失败 2,999 次。额外样本不加入预先约定的三轮平均值，但它证明当前连接池在 1000 个
线程同时借用 1000 条连接时会发生瞬时借用失败。协程版三轮、gRPC 同步版三轮和
gRPC 异步版三轮均为 1,000,000 次成功、零失败。

因此，简历若只写本次 QPS 数据，可以写“三轮平均成功 QPS”；不应把 Krpc 线程版
描述为在该压力参数下始终零失败。

## 7. 如何理解结果

无业务耗时时，测试主要消耗在协议编解码、框架调度、线程/协程切换、连接管理和
loopback 网络栈。Krpc 协程版只比线程版高 4.28%，说明在当前实现中，协程显著降低
线程数量的价值没有等比例转化成纯 QPS 优势；此时单次 RPC 很短，协程调度、Hook 和
共享连接池竞争也都进入热点路径。

Krpc 与 gRPC 的协议和连接模型并不相同。Krpc 使用较轻的自定义 TCP + Protobuf 帧，
并以 1000 条预热连接支撑 1000 个在途调用；gRPC 使用 HTTP/2、元数据、状态处理和
CompletionQueue，并通过原生 Channel 多路复用。这里保留各框架的原生工作方式，是
端到端框架对照，而不是只比较 Protobuf 序列化速度或相同连接数下的网络微基准。

最初一次 gRPC 同步采样把 `MAX_POLLERS` 设为 400。经核对 gRPC 1.51.1 源码，该参数
作用于每个 CQ；4 个 CQ 理论上允许约 1600 个 poller。该组平均值 16,211.9 QPS 已废弃，
上表是按每个 CQ 最多 100、总计约 400 个 poller 重新测试的结果。过多线程没有提高
吞吐，反而增加了调度开销。

## 8. 固定 4 ms 业务耗时

4 ms 测试保持 1000 逻辑并发、每轮 100 万请求和 400 个阻塞业务工作线程。Krpc 使用
独立的 `krpc_delay_server`，没有修改原 `Kserver.cc`。gRPC 异步服务端把业务等待放到
独立的 400 线程业务池，避免直接阻塞仅有的 4 个 CQ 消费线程。

| 端到端调用链 | 三轮成功 QPS | 平均成功 QPS |
| --- | ---: | ---: |
| Krpc 线程客户端 -> Krpc Provider | 46,693.0 / 57,136.6 / 45,157.1 | **49,662.2** |
| Krpc 协程客户端 -> Krpc Provider | 61,013.2 / 58,244.8 / 53,671.9 | **57,643.3** |
| gRPC 同步客户端 -> gRPC 同步服务端 | 16,181.2 / 16,791.2 / 16,723.7 | **16,565.4** |
| gRPC 异步客户端 -> gRPC 异步服务端 | 26,373.0 / 28,054.6 / 31,266.3 | **28,564.6** |

4 ms 条件下的横向比较：

| 比较组 | 结果 |
| --- | --- |
| Krpc 协程版 vs Krpc 线程版 | 协程版高 **16.07%** |
| Krpc 同步线程版 vs gRPC 同步版 | Krpc 高 **199.80%**，约为 gRPC 的 **3.00 倍** |
| Krpc 协程版 vs gRPC 异步版 | Krpc 高 **101.80%**，约为 gRPC 的 **2.02 倍** |

相对各自无业务平均 QPS 的变化：

| 实现 | 加入 4 ms 后的变化 |
| --- | ---: |
| Krpc 线程版 | **-8.53%** |
| Krpc 协程版 | **+1.81%** |
| gRPC 同步版 | **-15.63%** |
| gRPC 异步版 | **-34.06%** |

Krpc 协程版的 `+1.81%` 不是“加了业务反而更快”的可靠结论，它小于当前环境的轮次
波动，应视为基本持平。400 个业务线程执行 4 ms 等待的理论容量约为 100,000 QPS，
仍高于实测值，因此 Krpc 此时还没有被 4 ms 业务池容量完全限制。gRPC 同步版仍接近
16k，说明当前同步客户端/单 Channel HTTP/2 路径已经是主要瓶颈。gRPC 异步版则从
43,321.9 降到 28,564.6，业务等待已经明显进入吞吐关键路径。

4 ms Krpc 线程版三轮失败数分别为 3,804、131、0；协程版分别为 0、0、710。第三轮
协程客户端打印的 53,710.0 是总请求 QPS，表中按成功数重新计算为 53,671.9。gRPC
同步和异步六轮均为零失败。

4 ms 测试命令：

```bash
./framework-benchmark/build/bin/krpc_delay_server -i ./bin/benchmark-1000-business-400.conf
./bin/client -i ./bin/benchmark-1000-business-400.conf
./bin/coroutine_client -i ./bin/benchmark-1000-business-400.conf

./framework-benchmark/build/bin/grpc_sync_server 127.0.0.1:9000 4 100 4
./framework-benchmark/build/bin/grpc_sync_client 127.0.0.1:9000 1000 1000

./framework-benchmark/build/bin/grpc_async_server 127.0.0.1:9001 4 1000 4 400
./framework-benchmark/build/bin/grpc_async_client 127.0.0.1:9001 1000 1000 4
```

## 9. 压测程序审查与适用边界

当前四个客户端的请求数量、逻辑并发、成功判断和墙钟计时逻辑是成立的。同步客户端
均把 1000 个线程的创建和回收计入时间；Krpc 协程和 gRPC 异步客户端也都把调度工作
线程启动、任务投递及全部 RPC 完成计入 RPC 阶段。请求和响应字段编号、内容及
Protobuf 线类型等价。

但这不是严格的同协议微基准，仍有以下条件差异：

- Krpc 用 1000 条预热 TCP 连接；gRPC 的所有 Stub 共享一个 Channel，通过 HTTP/2
  多路复用。这是当前两个框架的原生连接模型，也是 gRPC 数字较低的重要测试条件。
- Krpc 客户端每次请求还执行 ZooKeeper 本地服务缓存查询、一致性哈希、连接池借还和
  延迟样本记录；gRPC 客户端每次创建 `ClientContext` 并处理 HTTP/2 元数据和状态。
- Krpc 服务端是 Muduo + 4 个 I/O 线程 + 400 业务线程；gRPC 同步与异步服务端采用
  各自的原生调度模型。比较的是完整框架，而不是只替换客户端。
- 客户端与服务端运行在同一台 8 vCPU 虚拟机上，会竞争 CPU；虚拟机调度、动态频率、
  连接批量关闭和服务端连接日志都会造成轮次波动。
- 当前只预热连接，没有预热一段 RPC 流量；三轮算术平均能减少偶然性，但不足以达到
  严格性能报告的稳定程度。

因此这些程序适合回答“我的两个完整实现，在这台机器和这组参数下能跑多少”，不适合
代替 gRPC 官方极限性能数据，也不能用来证明协议本身快多少。

ApacheBench 和普通 wrk 不能直接用于这里：它们生成 HTTP/1.x 请求，不理解 gRPC 的
HTTP/2 消息帧，也不理解 Krpc 自定义二进制协议。只压 gRPC 服务端可以使用 `ghz` 或
gRPC 官方 benchmark 的 driver/worker；但它们不能调用 Krpc。若目标是比较 C++ 同步
客户端与协程客户端，客户端本身就是被测对象，使用自写 C++ 压测客户端是合理的。
更正式的做法是把客户端和服务端放到两台机器，关闭请求级日志，先预热 RPC，固定 CPU
频率和亲和性，运行 5 到 10 轮并报告中位数，同时始终保留失败请求统计。

## 10. 2026-07-27 无业务复测

本次复测继续使用 Release、1000 逻辑并发、每轮 100 万请求、400 个服务端业务线程和
1000 条预热长连接。与第一次测试相比，服务端日志重定向到 `/dev/null`，并在相邻客户端
轮次之间等待 3 秒，让上一轮连接先完成清理。线程版与协程版交替运行，各执行三轮。

| 轮次 | Krpc 线程版成功 QPS | Krpc 协程版成功 QPS |
| --- | ---: | ---: |
| 1 | 58,389.3 | 61,535.2 |
| 2 | 55,283.0 | 53,852.2 |
| 3 | 47,284.6 | 65,202.5 |
| 三轮平均 | **53,652.3** | **60,196.6** |
| 三轮中位数 | **55,283.0** | **61,535.2** |

按三轮平均值计算，协程版增加 6,544.3 QPS，提升 **12.20%**；按对异常波动更稳健的
中位数计算，提升 **11.31%**。

线程版三轮失败数分别为 0、3、1,709，全部为 `Borrow connection from pool failed!`；
协程版三轮均为 100 万成功、零失败。第三轮线程版的连接池争抢和失败明显拉低了平均值，
第二轮则是线程版比协程版高。因此这次能报告的准确说法是“该次三轮复测平均提升
12.20%、中位数提升 11.31%”，不能把 12.20% 当作跨机器、跨轮次稳定不变的提升比例。

## 11. 2026-07-27 最终单轮结果

按最终约定，线程版和协程版各只执行一次。为避免前一个客户端给后一个客户端留下
连接、任务队列或 Provider 运行状态，两组分别使用全新启动的 Krpc Provider；每个
Provider 启动后等待 3 秒，服务端日志均重定向到 `/dev/null`。其他条件保持一致：
Release、无业务耗时、1000 逻辑并发、每轮 100 万请求、400 个服务端业务线程和
1000 条预热长连接。

| 实现 | 成功数 | 失败数 | 成功 QPS |
| --- | ---: | ---: | ---: |
| Krpc 线程版 | 999,999 | 1 | **63,445.6** |
| Krpc 协程版 | 1,000,000 | 0 | **70,085.7** |

本次单轮中，协程版增加 **6,640.1 QPS**，相对线程版提升 **10.47%**。适合本结果的
准确表述为：“在单机 1000 并发、100 万次无业务 RPC 的单轮测试中，成功 QPS 从
6.34 万提升至 7.01 万，提升 10.47%。”该数字是一次测量结果，不代表多轮统计稳定值。

| Krpc协程版 | 993,051 | 6,949 | 27.8343秒 | **35,677.2** |

协程客户端打印的`rpc qps: 35926.9`使用总请求数计算；本表按统一口径使用
`993051 / 27.8343 = 35677.2`成功QPS。本次单轮中，协程版成功QPS比线程版少
2,280.9，下降 **6.01%**。线程版失败全部为`Borrow connection from pool failed!`；
协程客户端当前不输出失败原因分类，因此不能把其6,949次失败全部归因于连接池。

该结果说明，在当前2 vCPU且系统已有Swap占用的环境中，1000逻辑并发已经出现明显失败，
不能沿用8 vCPU环境下“协程版QPS提升”的结论，也不适合作为稳定容量数据。

## 15. 2026-07-28 反序单轮测试

为验证协程版失败是否由测试顺序造成，本轮先测协程版、后测线程版。两边仍各执行一次，
分别使用全新Provider；Provider启动后等待5秒，协程版完成后停止Provider并等待30秒，
再启动新的Provider测试线程版。其他条件与上一节一致。

| 实现及顺序 | 成功数 | 失败数 | RPC耗时 | 成功QPS |
| --- | ---: | ---: | ---: | ---: |
| Krpc协程版（先测） | 989,952 | 10,048 | 28.3199秒 | **34,956.1** |
| Krpc线程版（后测） | 1,000,000 | 0 | 26.9010秒 | **37,173.3** |

协程版打印的`rpc qps: 35310.9`是总请求QPS；成功QPS按
`989952 / 28.3199 = 34956.1`计算。本轮协程版比线程版低2,217.2 QPS，下降 **5.96%**。

协程版改为先测后，失败数由上一轮的6,949增加到10,048，而后测的线程版变为零失败，
因此可以排除“协程版因排在线程版后面受到残留状态影响”这一解释。当前协程客户端只在
失败分支增加总计数，没有记录`Krpccontroller::ErrorText()`；在增加失败原因分类前，无法
继续区分连接池借用失败、发送/接收失败、I/O超时或响应解析失败。

## 16. 2026-07-28 协程失败原因诊断

在协程压测客户端的失败分支增加`Krpccontroller::ErrorText()`分类，以及每类失败的平均
和最大耗时统计。成功路径不加锁。Release重新构建后，使用全新Provider单独执行一次
协程客户端，结果如下：

| 指标 | 结果 |
| --- | ---: |
| 总请求数 | 1,000,000 |
| 成功数 | 990,651 |
| 失败数 | 9,349 |
| 成功QPS | 33,949.2 |
| 失败原因 | `Borrow connection from pool failed!` |
| 该原因次数 | 9,349 |
| 平均失败耗时 | 0.000570801 ms |
| 最大失败耗时 | 1.9668 ms |

全部失败均发生在连接池借用阶段，且耗时远低于3秒RPC超时，因此本轮可以排除Hook
定时器超时、发送失败、接收失败和响应解析失败。直接原因是连接池的空闲队列在高并发
借用时返回空，而达到连接上限或动态建连未成功后，`BorrowConnection()`立即返回`-1`；
当前实现没有连接等待队列，也不会挂起调用协程等待其他请求归还连接。

## 17. 2026-07-28 4 vCPU、8 GB环境单轮测试

虚拟机调整为4 vCPU、7.21 GiB系统可见内存（标称8 GB），Swap为0。按与2核反序测试
相同的顺序先测协程版、后测线程版，两边各执行一次，不预跑、不补跑；两组分别使用
全新Provider，Provider启动后等待5秒；协程版结束后停止Provider并等待30秒，再启动
新的Provider测试线程版。其他条件仍为Release、无业务耗时、1000逻辑并发、每版100万
请求、400个服务端业务线程和1000条预热长连接。

| 实现及顺序 | 成功数 | 失败数 | RPC耗时 | 成功QPS |
| --- | ---: | ---: | ---: | ---: |
| Krpc协程版（先测） | 1,000,000 | 0 | 16.6001秒 | **60,240.4** |
| Krpc线程版（后测） | 1,000,000 | 0 | 18.2222秒 | **54,878.2** |

本轮协程版增加5,362.2 QPS，相对线程版提升 **9.77%**，两边均零失败。与顺序相同的
2 vCPU反序单轮测试相比，协程版从34,956.1提升至60,240.4，提升 **72.33%**；线程版
从37,173.3提升至54,878.2，提升 **47.63%**。连接池借用失败在本轮没有触发，说明增加
CPU资源显著改善了并发时序，但连接池无等待、瞬时取空即失败的设计仍未修复。
